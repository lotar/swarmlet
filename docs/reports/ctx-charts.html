Two-Mac split: context and concurrency

Measured on the live mesh, qwen3.8-27b split 12 layers (Apple M5 Pro, 24 GiB usable) + 52 layers and the coordinator (Apple M5 Max, 128 GiB), relay transport. Raw rows are in the two .jsonl files beside this page; the numbers below are read directly from them.

Two independent axes were measured: the context window (4K→256K, one caller) and the slot count (1→16, that many concurrent callers).

Read: decode rate does not change with the window (5.4–6.3 tok/s across 64×), prompt rate does not degrade with it, and the output hash is identical at every level — the configured window does not perturb results. Worker free RAM falls monotonically, so a worker does pay for context, via RPC-side buffers, even though the KV cache lives on the coordinator.

2 · Slot count / concurrency

The deployment's --parallel is the variable; exactly that many concurrent streaming requests were issued, so contention is present rather than assumed. TTFT is client-measured wall clock to the first content token.

All concurrency rows

Read: TTFT roughly doubles with each doubling of slots — slots serialize prompt evaluation rather than parallelising it. Aggregate saturates near 12–14 tok/s while the per-caller rate falls 6.4×. Context size makes no difference here: the two ctx values track each other within noise. All concurrent requests returned identical answers, so concurrency does not corrupt output.

Not measured, do not infer: relay bytes per token (the socket accounting failed in both sweeps), engine-side prompt/decode milliseconds on the streaming path, and anything at concurrency above 16 or with natural (non-repeated) prompt text.
