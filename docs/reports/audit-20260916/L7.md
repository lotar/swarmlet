## 4. SIMPLIFIED (survivors only)

Ordered by value per line changed.

**S1 — validate `serve`, and give `fill()` a `finally`.** 3 lines, prevents a permanent, silent disable.
`protocol/validate.ts` `case "worker"` validates `port/device/threads/memCapMiB/peerPort/peers[]` — **`serve` is not validated at all**, although `checkEndpoint()` already exists and is used for `peers[]` and `rpc[]`. `servedial.ts:59` then dereferences `target.direct.length`, and `fill()` (`servedial.ts:54-74`) sets `this.filling = true` with **no `try/finally`** — `stop()` does not clear it either. Fix: `checkEndpoint(a.serve, "serve")` when present, and wrap `fill()`'s body in `try { … } finally { this.filling = false; }`.

**S2 — one number, one owner for RAM.** Today three memory controls feed one process: (i) planner `ramShortfall()` (`control/planner.ts:310-314`) rejects a darwin placement needing more than the *available* offer, (ii) the agent's watchdog caps at `enforce.ramMiB` (= allocation, else the whole offer), (iii) the engine gets `--mem-cap-mib <gpu.memMiB>` (`planner.ts:453` → `recipes.ts:24`). (i) and (ii) agree by construction (`enforce.ramMiB` = the plan's allocation — not two places that can disagree), so the duplication is deliberate defence in depth and should stay; what is wrong is that (ii)'s fallback is the whole machine. The live case shows the gap: cap 116 GiB, admitted fit 31 GB, box 128 GB, co-tenants (mlx :8112/:8116, ollama) sharing it. Keep the duplication, delete the coarse fallback.

**S3 — `dataListener.ts` serve branch calls `sock.setNoDelay(true)` a second time** (line 68; already set for every connection at line 40). 1 line.

**S4 — `attachLocal()`'s parked-stream pool is 4× the demand.** `SERVED_QUEUE_MAX = 12` (`dial.ts:42`) vs 3 rpc endpoints on the live coordinator; a full queue refuses the *newest* offer (`dial.ts:83-88`) so the peer re-offers every 3 s (`servedial.ts:29 RETRY_MS = 3000`, max 6). Class B: the mechanism is inferred from code + counts, not proven (needs one run with the flag on).
