01

You are renting capability you paid for twice.

Frontier APIs are a lease with no equity. The price changes, the model is deprecated, the region is blocked — and every workflow you built quietly accrues value for the vendor, not for you. Five problems, one architectural answer.

01 — Rented

Capability is leased, never owned

Workflows built on an endpoint that can reprice, deprecate or geo-block overnight. Nothing accumulates on your side of the wire. The model is the least durable component in the stack — a new generation ships roughly every four months and obsoletes every fine-tune built on its predecessor.

02 — Exfiltrated

The data leaves the building

For an EU SME, sending customer contracts, case files or internal code to a third-party inference endpoint is a liability you carry, not a feature you get. For an individual it is a privacy tax paid in exchange for competence.

03 — Amnesiac

AI does not learn your work

Frontier models are stateless generalists. The 20–30 processes your team repeats weekly are exactly where a specialist wins — and no product systematically builds that specialist out of daily usage. Every session starts from zero.

04 — Unreliable

Small models fail where it counts

Raw local models rank mid-pack overall and near the bottom of their cohort on agentic tasks. That gap is real. It is closed by architecture — retrieval, verification, best-of-n, routing — not by hoping the next quant behaves.

05 — Untrusted

No trust fabric for shared improvements

Thousands of community fine-tunes exist. They are opaque, unauditable, non-composable, and impossible to evaluate against your data before installing. The sharing economy for model improvements is stalled on trust, not on supply. Swarmlet's answer: share recipes, never weights — and decide by measurement, not by reputation.

02

The inversion

Everyone else bets on models. We bet on everything around them: own the knowledge and the verification, rent the intelligence, give away the recipe — and make all of it survive the thing everyone else is betting on.

Governing design test, applied to every feature: does it survive a base-model swap untouched? If not, it lives in the disposable layer and must be regenerable automatically.

03

Five layers. Each one ships alone. Each one survives the death of the layer below it.

The harness is TypeScript on Bun with zero runtime npm dependencies — development-only type packages are pinned. The knowledge store is a plain git repo of markdown. The event store is one SQLite file per node. Signing is ed25519. There is no database to migrate and no service to hold hostage.

L0

Model contract

Permanent · published source-available spec

An OpenAI-compatible endpoint plus a capability manifest: context length, tool calling, modalities, quantization, whether the thing is even MoE. The manifest is probed at runtime from /v1/models and config — never hardcoded per model. llama.cpp serves it on Metal today; an EU-resident frontier proxy is the same interface with a different base URL.

Why

The base model is the least durable component in the whole stack. So no value may be stored in it. The intended Qwen 3.6 → 3.8 swap flow is re-baseline evals and re-audition adapters; the current alpha provides the underlying contracts and gates, not a finished one-command swap.

  • OpenAI-compatible chat completions, pinned seeds, temperature 0 for evals
  • Planned release gate: make the swap procedure an executable command rather than a wiki-only checklist
  • Q8 quantisation chosen over Q4: precision over storage on the reference node
  • Measured native MTP Q4 n=3: 43.71 tok/s on one campaign prompt; concurrency results are reported separately
L1

Knowledge layer

Permanent · free · compounding

A git repository of markdown: skills/, memory/, an immutable system.md. Every artifact carries trigger→outcome provenance — which real events motivated it and what result it produced. Versioning, rollback, blame and audit are git's problem, solved since 2005. A GDPR right-of-access request becomes git show.

Why

This is where self-improvement actually lives for the first year. Weight updates are slower, riskier and disposable; text skills are instant, auditable, reversible and survive every model swap. Optimised skill artifacts have been shown to transfer across model scales and across harnesses — the asset follows you.

  • Commit schema: refine(type): one-liner + trigger: / evidence: lines
  • Revert by SHA. Provenance is grep-able forever.
  • PII is triaged before it can ever reach L1 prose
  • system.md is committed once and protected — the gate refuses edits to it
L2

Verification layer

The moat · freemium

Three mechanisms, each killing a specific attack. An eval generator, not an eval suite: the alpha implements six task templates plus metamorphic transforms (paraphrase, HR↔EN translation, field permutation, value scaling, format shift) with property-based checks. The next-phase target is ~200 templates and freshly sampled ~5k-instance release gates. Private per-node shards: the alpha proves isolated local shards and audition on deterministic fixtures; auto-building ~50 tasks from each customer's real data is the next deployment phase. Foreign artifacts are admitted by local audition — an overnight trial against your shard, activated only if they beat the incumbent on your distribution. Behavioral-diff certificates: probe broadly outside the claimed domain; large off-domain drift is an automatic reject.

Why

A fixed suite becomes the training target — for honest adapters and for adversaries alike. You cannot overfit a distribution you never see twice: frozen in design, moving in instances. And predicting whether a foreign adapter fits your data is genuinely unsolvable by cheap classifiers, so audition does not predict — it measures. The unsolvable problem is deleted, not solved.

  • Deterministic scoring: same engine as serving, so no train/test skew
  • Noise-aware three-way verdict (accept / keep / revert) with a one-sided ~95% binomial margin over paired instances
  • A single flipped instance can never be misread as a regression; ties keep the incumbent
  • Gate certificates are ed25519-signed JSON, retained per node
  • Classifiers narrow the field cheaply; the deterministic gate decides. The gate never learns.
L3

Weight layer

Disposable by design

LoRA adapters, one active per request, admitted only through L2 audition. Trained only when a pattern saturates — 20+ occurrences spread over weeks, with provenance evidence that a text-level skill was tried and the pattern still recurs. Discarded at base swap and regenerated overnight: the L1 skills plus logged trajectories are the recipe.

Why

Adapters are cache, not state. That dissolves depreciation — models getting better is now a free upgrade absorbed on swap day — and it dissolves the data-scarcity problem too: one node's daily signal is far too thin for nightly weight training anyway. Training data is distilled and corrected samples, never raw self-outputs. That is the anti-collapse measure.

  • MLX-LM LoRA on Apple Silicon, Unsloth QLoRA on CUDA nodes · 40–60 GB overnight budget
  • Exported back to GGUF for the same L0 server
  • Composition via merging is unsolved — we sidestep it (one active), we do not claim to solve it
  • Saturation detector enforces every PRD condition before a single gradient step
L4

Mesh & commons

The masses · sequenced last

The community source is free for personal and noncommercial use, and for Commercial Use while the Corporate Group's Worldwide Gross Annual Revenue is not more than EUR 1,000,000, as defined in the licence. Skill packs, eval templates and adapter recipes are text artifacts each node can inspect and execute locally. The mesh contributes idle GPU cycles to two workloads: distributed eval certification (embarrassingly parallel, churn-tolerant, 5% of tasks triple-run and cross-checked) and thin-client serving for people who own no capable hardware.

Why

Distribution "to the world" fails as weights — incompatible LoRA piles — and succeeds as knowledge plus verification. Private eval inputs never leave a node; opt-in aggregate pass rates and signed recipes or skills may leave, and deliberately escalated prompts follow the configured frontier-provider boundary. That produces honest transferability scores nobody can game, including the authors, because no one knows the shard contents.

  • Logical nodes are separate OS processes with their own SQLite state, Ed25519 keys, knowledge clone and private shard
  • SIGKILL one node mid-certification: the in-flight instance is requeued, run completes
  • Eval traffic is a better mesh workload than inference — no latency SLA, perfect parallelism
  • Explicit gate: revenue justifies this phase, not architecture elegance
04

The loop that improves itself, on one box, offline.

Six steps, three OS-native schedules — launchd or systemd timers, no resident daemon, trivially auditable, crash-resumable. Two-tier promotion: memories clear a fast smoke suite and activate the same day; skills and subagent specs wait for the nightly full gate. Near-real-time where it is safe, gated where it is not.

STEP 01

Capture

Every agent session appends events to SQLite: user corrections, retries, tool failures, outcome signals. Append-only, single file, one per node.

Continuous

STEP 02

Curate

A local-model judge triages signal from noise, flags PII before it can reach knowledge prose, and extracts skill candidates: “this failed again because…”.

Every 3 hours

STEP 03

Refine

The smallest CRUD edit to the knowledge repo — add, amend, split or delete one artifact — committed to git with trigger and evidence provenance.

On candidate

STEP 04

Gate

Fresh-sampled evals, old versus new, deterministic scoring. Regression → automatic revert and a signed certificate recording the failure.

Nightly

STEP 05

Graduate

Saturation detector: ≥20 occurrences, ≥7-day spread, evidence a text skill was tried and the pattern still recurred. Only then an adapter recipe.

On saturation

STEP 06

Publish

Passing artifacts — recipes and skills, never weights — optionally leave the node, signed, for audition somewhere else.

Opt-in

Kill switch: eval trend flat or declining across three consecutive gates → refine freezes and the audit is the work.Immutable core: the gate refuses edits to system.md.

07

A mesh of sovereign sites, not a distributed monolith.

What is proved, and what is not.

  • Proved in one-host simulation: three self-contained CPU site containers with independent code, keys, SQLite state and private eval shards — 8/8 acceptance, 16.6 s certification.
  • Proved in one-host simulation: three dedicated native Metal sidecars, one per logical European Docker node, each with its own model mapping, KV cache, port and lifecycle.
  • Proved: per-expert ownership — each isolated worker process owns specific expert IDs, rejects foreign IDs and returns deterministic partials for coordinator-side reduction.
  • Measured, not claimed: Docker Desktop's WebGPU bridge returned a correct 1024×1024 integer matmul in 42.5 ms on this machine — real host GPU forwarding. The pinned llama.cpp WebGPU backend is ABI-incompatible with the injected Dawn 2024 client, so we do not describe those containers as having direct GPU access.
  • Not downloaded, not loaded: the Kimi K3 frontier checkpoint. That study is architecture research against published facts, labelled as such.

08

Claims, calibrated. Including the ones that lose us the sale.

A 27B will not match a 2.4T model on arbitrary tasks. Anyone claiming otherwise is selling you something; the ~100× compute gap is not closable by harness work. The product wins by making that comparison irrelevant for most real usage, and by routing the remainder honestly.

Frontier-level on general benchmarks, single node

No — ever, this hardware class

Not closable by architecture. We refuse the claim instead of softening it.

Frontier-level on your own recurring, verifiable workflows

Yes — ~2–3 months of loop runtime

Specialist depth beats generalist breadth on a narrow distribution. Verification plus best-of-n is worth 10–20 points on checkable tasks; the ramp precedent shows a small RL model beating frontier on one team's workflow.

Frontier-level aggregate coverage across the network

Plausible — years

The shared skill and eval layer compounds monotonically, and every base-model swap imports that generation's gains for free. Economically valuable work is concentrated in repeated, verifiable workflows.

Open-ended novel reasoning

Routed out — shrinking

Where no verification can be defined, the router escalates to a frontier API instead of pretending. The dependency shrinks every generation and the architecture absorbs the shrinkage without redesign.

What this architecture refuses to pretend

  • 01
    Adapter composition is unsolved. Merging LoRAs is weight arithmetic, not a decision problem. We sidestep it with one active adapter per request — we do not claim to have solved it.
  • 02
    Poisoning risk asymptotes, it never reaches zero. Audition plus behavioral-diff certificates plus signed provenance reduce it to software-supply-chain levels. Same as every dependency you already ship.
  • 03
    The gate never learns. Anything that changes weights or executes irreversibly is decided by the expensive dumb thing — the one component whose failure modes do not move with the attacker. A refinement loop optimises whatever it can reach; we have seen what that produces when it finds an exploit.
  • 04
    Network effects are not conjured by a roadmap. The mesh is sequenced last and gated on revenue. The commons delivers “free AI for the masses” before the mesh exists, as artifacts you can run on your own machine today.
  • 05
    The last 1% is execution. No document de-risks it, including this one.

11

Objections, answered where they land.

Why not just call a frontier API?

Because nothing accumulates on your side. The endpoint can reprice, deprecate or geo-block, and your workflows are the training signal for someone else's moat. If your work is genuinely one-off and open-ended, call the API — Swarmlet routes that tier out honestly rather than pretending. If 20–30 of your processes repeat weekly and have a checkable definition of done, a specialist on your own hardware with your own verification wins on those tasks and the asset stays with you.

Why is a 7B model enough to prove the architecture?

A 27B proves nothing about harness quality that a 7B-A1B cannot prove cheaper and faster. If refinement plus verification plus routing measurably lifts a tiny sparse model on narrow recurring workflows, the same machinery lifts every larger generation — for free, on swap day. The MoE choice additionally stress-tests the L0 contract on a non-dense architecture, and the planned swap to a different vendor's tiny MoE doubles as the first live rehearsal of the base-swap procedure.

Won't self-improvement collapse into its own echo?

It will, if the loop feeds itself. Three structural stops: training data is distilled and corrected samples — a stronger model's rewrite of a lesson, never raw self-output; the deterministic gate sits outside the loop and never learns; and a kill criterion freezes refinement after three consecutive flat-or-declining gates. A refinement loop optimises whatever it can reach — the published cautionary tale is an agent that built highly efficient cheating skills once it found an exploit. We treat that as a design input, not a curiosity.

How is my data handled?

Private eval inputs stay on the machine by default and curation flags PII before anything can reach knowledge prose. Aggregate pass-rate statistics or anonymised artifacts leave only when you opt in. If you deliberately enable managed frontier fallback, the escalated prompt leaves the machine for that configured provider; the router must make that boundary visible. The knowledge layer is a git repo of markdown, so a data-access request is git show rather than forensic archaeology.

What stops a shared adapter from poisoning my node?

Three layers, and one refusal: weights are never shared — only recipes, which your node executes locally. Foreign candidates face a local overnight audition against your private shard and activate only if they beat the incumbent on your distribution. Behavioral-diff certificates probe broadly outside the claimed domain, because a trigger's existence perturbs the function somewhere. Residual risk sits at software-supply-chain level, same as any dependency you already ship — not zero, and we will not claim otherwise.

What hardware do I actually need?

For the owner-operator tier: an Apple Silicon box with ~64 GB unified memory or a 24 GB+ CUDA card runs the harness and a Q8 quant of a 27B class model, with headroom for overnight QLoRA. Sovereign CPU sites run too — measurably slower (41.3 ms per output token on a 2-core Docker cap versus 3.3 ms on the local GPU) but fully independent of any host GPU. The thin-client mesh tier exists for people with no capable hardware at all.

Is the mesh live today?

No. Three logical nodes plus a coordinator run as separate OS processes on one machine, over simulated pan-EU latency, with churn drills and redundant-execution certification — that is the accepted P0a simulation. Public rule: no distributed-compute claim before that simulation passes, and P4 changes the topology, not the logic. Deployment of real multi-site mesh is gated on revenue, not on our enthusiasm.

What is the stack?

llama.cpp llama-server for inference (OpenAI-compatible, Metal, speculative decode), TypeScript on Bun with zero runtime npm dependencies for the harness, a plain git repo of markdown as the knowledge store, SQLite in WAL mode per node, ed25519 signatures on every artifact and gate certificate, MLX-LM and Unsloth for LoRA, launchd or systemd timers as the scheduler. Docker Compose topologies for sovereign CPU sites and GPU-site simulation.
